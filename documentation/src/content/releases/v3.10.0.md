# v3.10.0: New no-inline-signature-types rule for inline object types

This release adds the `no-inline-signature-types` naming rule, which reports object type literals written inline in parameter and return type annotations. No existing rule changed.

## 🚀 Added
- **no-inline-signature-types**: The rule reports an object type literal written inline in a parameter or return type annotation, such as `function formatLabel(options: { label: string }) {}`, and asks for a named interface instead. `function formatLabel(options: LabelOptions) {}` passes. - by @howmanysmall in [#106](https://github.com/howmanysmall/small-rules/pull/106)

The rule takes three options:
- `functions`: `"all"` (default) checks every function and signature. `"components"` checks only PascalCase function components and the callbacks passed to `memo` or `forwardRef`.
- `position`: `"anywhere"` (default) also looks inside unions, intersections, arrays, and tuples. `"bare"` reports only an annotation that is the object type itself. `"wrapped"` also reports an object type inside a generic such as `Readonly<{ label: string }>`.
- `returnTypes`: `true` (default) also checks return types, including the type in a `value is ...` predicate. Set `false` to check only parameters.

Once enabled, the rule reports every existing inline object type in the checked positions. Declare a named interface for each one, or leave the rule off.
