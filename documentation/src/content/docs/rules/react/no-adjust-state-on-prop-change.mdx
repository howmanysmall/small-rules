---
title: "No Adjust State on Prop Change"
---

import RulePage from "$components/rule-page.astro";

<RulePage rule="no-adjust-state-on-prop-change">
	<Fragment slot="rationale">
		<p>
			Ported from{" "}
			[`eslint-plugin-react-you-might-not-need-an-effect/no-adjust-state-on-prop-change`](https://github.com/nickjvandyke/eslint-plugin-react-you-might-not-need-an-effect/blob/2fc3560bbd24898b883e6e8fa31e8c5429b02753/src/rules/no-adjust-state-on-prop-change.ts).
			The upstream rule points at the ["Adjusting some state when a prop
			changes"](https://react.dev/learn/you-might-not-need-an-effect#adjusting-some-state-when-a-prop-changes)
			section of the React docs.
		</p>
		<p>
			It flags an effect whose dependencies include a prop, and whose body synchronously writes state. It's a
			prop-to-state sync. It costs two renders. The prop arrives and you render with the old state. Then the
			effect runs and you render again with the fixed one. During that gap, the UI shows state that's already
			wrong. On Roblox that shows up as a textlabel or a frame popping in a frame late.
		</p>
		<p>
			The fix is to not copy the prop into state at all. Compute what you need during render and let the prop stay
			the source of truth. If the state has its own lifecycle, there are better tools than an effect for resetting
			it. More often the state shouldn't exist.
		</p>
	</Fragment>
</RulePage>
